# Core Concepts

## Scope vs Input

Every file in a Wolder project is one of two things:

| Concept | Description | Ownership | LLM can write? |
|---------|-------------|-----------|----------------|
| **Scope** | Files the LLM generates or modifies | Framework | Yes |
| **Input** | Files the developer writes and maintains | Developer | No |

This boundary is what makes manual edits safe. You put hand-authored code in input files and reference them as context. The LLM receives them as read-only context and cannot modify them.

```typescript
// Input — developer-owned, never touched by Wolder
const todoModel = w.input("src/models/TodoItem.ts")

// Scope — generated by Wolder, can be overwritten
w.scope("src/services/todoService.ts")
```

## Artifacts

An **artifact** is the return value of `build()`. It carries:

- **id** — derived from the scope file paths
- **outputHash** — SHA256 of the generated file contents
- **generatedFiles** — list of files that were written
- **members** — typed references to code elements (classes, methods)

```typescript
const svc = await w
  .scope("src/services/todoService.ts")
  .act("Create a TodoService class")
  .expectClass("TodoService")
  .withFunction("getAllItems")
  .withFunction("addItem")
  .build()

svc.members.getAllItems  // MemberRef<"getAllItems"> — fully typed
svc.members.addItem     // MemberRef<"addItem">
svc.members.oops        // Compile error — not a declared member
```

Member types are inferred from `withFunction`/`withMethod` calls in the chain via TypeScript generics. No code generation step needed for single-expression chains.

## The DAG

Every generation program implicitly defines a directed acyclic graph:

- **Nodes** — individual `scope().act().expect*().build()` chains
- **Edges** — `withInput(artifact)` calls that wire one artifact's output as another's input
- **Cache keys** — content hashes of all inputs to a node

```typescript
// Node A: generates the service
const service = await w
  .scope("src/services/todoService.ts")
  .act("Create TodoService")
  .withInput(todoModel)
  .build()

// Node B: depends on Node A
const controller = await w
  .scope("src/controllers/todoController.ts")
  .act("Create controller")
  .withInput(service)  // ← dependency edge
  .build()
```

When Node A regenerates and its output changes, Node B is automatically marked stale. Wolder tracks these edges in the manifest via the `dependsOn` field.

## Caching

Wolder uses `wolder.manifest.json` as its cache. For each node it records:

- **inputHashes** — SHA256 of the act instruction, each input file's content, upstream artifact hashes, and the model name
- **outputHash** — SHA256 of the generated output files

On each `build()` call, Wolder computes the current input hashes and compares against the manifest. If they match, generation is skipped entirely.

**What causes a cache miss:**
- Changing the `.act()` instruction text
- Modifying an input file referenced via `.withInput()`
- An upstream artifact regenerating with different output
- Switching the model

**What does not cause a cache miss:**
- Renaming variables in your program file
- Adding comments to the program
- Reordering `.withInput()` calls

## Expectations

Expectations are structural assertions about generated code. They serve two purposes:

1. **Validation** — verify the LLM output meets requirements
2. **Retry feedback** — when expectations fail, error details are fed back to the LLM for a retry

Expectations run in a specific order, stopping at the first failure:

1. `expectFile(path)` — file exists on disk
2. `expectCompiles()` — `tsc --noEmit` passes
3. `expectClass(name)` / `expectInterface(name)` / `withFunction(name)` / `withMethod(name)` — AST structure via ts-morph
4. `expectImplements(interfaceRef)` — semantic type check via ts-morph
5. `expectWebPage(route, description)` — Playwright browser validation (most expensive, runs last)
